#
# The gate (tests/unit/test_service_rejection_messages_i18n.py) flags every
# ``raise ValueError('<sentence>')`` in any non-test module; a line here is
# the only way a site passes. The ledger is DEBT, not permission:
#   * a new client-facing refusal must raise ServiceRejectionError('<key>')
#     instead — the 400 envelope translates keyed rejections and stamps lang
#     truthfully;
#   * this file lives in the directory the baseline ratchet scans, so
#     appending a line fails the build until `manage.py arch lint
#     --write-baseline-sizes` is consciously run;
#   * entries are regenerated by `manage.py arch lint --write-rejection-
#     ledger` (same scan the gate runs); prose above the counts block is
#     hand-written, entries and counts below it are not;
#   * entries are ``relpath::literal`` — literal text, spaces included,
#     newlines stored escaped.
#
# Group 1 is empty: every refusal a request can reach through the 400 handler
# is keyed, and a client reads its machine code (the upper-cased key) in
# `detail.code`. What is left below is filed with the reason it is not a 400
# refusal: a Pydantic validator (422), a core guard, or an internal invariant.
#
# A sentence raised while the process boots, a manage.py command runs or a
# manifest or seed profile is validated is not debt of this ledger at all:
# nothing in a request reaches it, so it raises OperatorError
# (app/core/operator_error.py), a ValueError for the callers that catch one and
# not reader-facing at runtime. A new plain ValueError sentence in app/cli/,
# app/config.py or the manifest code is flagged by the gate like any other.
#
# Groups are assigned per REACHABLE MECHANISM, not per directory — a
# sentence in app/core/contracts reaches a client through the 422 validator
# envelope, so "core" alone was never a group:
#
# 1. client-400 — raised inside request handling; the global 400 handler
#    maps it to a client toast (app/modules, app/services, app/api). Pending
#    keyed migration, the way maker/production_service was migrated.
# 2. client-422 — Pydantic validator refusals reaching the client through
#    the 422 RequestValidationError envelope, a different path than the 400
#    envelope this gate guards (app/schemas, app/models, app/core/contracts).
#    Raw English here is real, tracked debt of the 422 class.
# 3. client-guards — core guards that fire during requests (imports,
#    uploads, SSRF checks, settings saves) and can reach the 400 envelope
#    the same way group 1 does; they head for the same keyed migration.
# 4. internal-invariant — a guard on a caller's mistake or on a model's
#    malformed answer; no request supplies the value. Plain on purpose: the
#    400 handler logs a plain ValueError with its traceback. Assigned per
#    entry in REJECTION_GROUP_OVERRIDES, never by path.
#
# The leaning is per path, not proven per site — in every group:
# re-check an entry against the client groups whenever its file
# changes for a client-facing reason. The known per-place exceptions are
# recorded as entry overrides in REJECTION_GROUP_OVERRIDES (the generator,
# app/core/architecture_lint/_quality_checks_rejections.py), which are
# consulted before the path rule:
#   * 'Provide exactly one of role or role_id' (app/api/organizations.py)
#     and 'reason must not be blank' (app/api/stock_lots.py) are raised
#     inside Pydantic validators, so they fly as 422s — filed under
#     client-422 despite the app/api/ path;
#   * 'Invitation not found' (app/services/_org_membership.py) stays in
#     client-400, but it does not fly as a 400 toast: both invitation
#     endpoints catch the refusal and answer the translated 404 of the
#     invitation resource. The line tracks the pattern until that
#     endpoint-side catch is migrated to a keyed rejection too.
